# Working Note: Legacy Keep/Cut and Minimal Strict-Side SM/GR Bridge

Status: working note, no false-pass intent
Date: 2026-03-19

## Scope

This note follows the current repo discipline from `K1`, `K2`, `T17`, and `S2`.
It does not reopen a mandatory `legacy -> strict` bridge program.
Its purpose is narrower:

1. keep only the parts of legacy that are still methodologically useful,
2. cut legacy claims that should no longer steer strict work,
3. define the smallest admissible strict-side bridge to SM/GR observables.

## What To Keep From Legacy

1. Keep `K_legacy_ont` only as a macroscopic/phenomenological nadsoliton-identification route, not as the current strict source kernel.
2. Keep the broad structural idea `oscillation + damping + hierarchy/fractal phenomenology` as a hypothesis family worth re-testing from strict-side sources.
3. Keep old successes only as benchmark targets or negative controls:
   mass ordering patterns, coarse flavor regularities, electroweak-angle touchpoints, gravity-hierarchy motivation.
4. Keep `4 ln 2` only where it is supplied by a strict-side source object (`alpha_geo_strict_derived_v1`), not as a legacy import.
5. Keep legacy failure modes and audit results as methodological guidance: they show where hidden calibration, circularity, or semantic transfer tends to enter.

## What To Cut From Legacy

1. Cut any silent transfer of legacy physical roles onto `K_strict_gate`.
2. Cut the old canonical tuple `(pi/4, pi/6, 0.01)` as a strict baseline unless rederived on the strict side.
3. Cut direct reuse of the legacy formulas
   `sin^2(theta_W) = alpha_geo / 12`,
   `alpha_EM^-1 = alpha_geo/(2*beta_tors)*(1-beta_tors)`,
   and exact `beta^N` gravity hierarchy
   as if they were current strict derivations.
4. Cut `gamma ~= 1.52`, quarter-octave mass-ladder claims, and local legacy `d` hits such as `2.25/2.33` from any proof role unless they are re-expressed through explicit strict invariants.
5. Cut the idea that strict closure must first solve legacy semantic inheritance before touching SM/GR observables.
6. Cut any practice where an old numerical hit is treated as theorem-level support without a current strict provenance chain.

## Minimal Strict-Side Bridge To SM/GR

The minimal bridge should not be a full "SM match" claim.
It should be a finite strict-side observable bridge layer with explicit provenance.

### A. Strict inputs only

Use only:

1. `K_strict_gate(d) = cos(omega*d + phi)/(1 + beta*d^eta)`,
2. strict-side nadsoliton ontology (`AX9/F1` lane),
3. strict-side `alpha_geo_strict_derived_v1 := 4 ln 2`,
4. explicit strict selector/symmetry-breaking premises only if they are declared as such.

### B. Bridge intermediates

Build a frozen registry of strict intermediates:

1. kernel invariants,
2. micro-supported quantities,
3. radiative/intersection quantities,
4. shared-basis objects only when their provenance is explicit.

No hidden legacy literals may appear in this layer except as historical comparison labels.

### C. Minimal host-observable set

Start with a very small set of bridge targets:

1. mass-ratio / ordering observables,
2. `sin2_theta_w_eff` as a strict-side candidate observable,
3. `alpha_s` boundary observable,
4. one dimensionless gravity bridge observable.

`CKM/PMNS` may be kept as an extension layer, but they should not define the minimum bridge unless their no-fit provenance is genuinely closed.

### D. Unit discipline

Stop the strict bridge at dimensionless or explicitly normalized observables.

1. `proxy -> GeV` calibration stays outside the minimal strict bridge,
2. SI conversions stay tagged as external-definition or anchor layers,
3. host matching is not the same thing as strict derivation.

## No-False-Pass Rules

1. Freeze the bridge map before comparison to host observables.
2. Do not rescan parameters after declaring the bridge target set.
3. Give every target one explicit status label:
   `strict-derived`, `strict-derived-with-external-observable-origin`,
   `anchor-dependent`, `si-definition`, `non-strict`, or `open`.
4. Legacy formulas may appear only as benchmark hypotheses, not as derivation steps.
5. If provenance is incomplete, mark the result `partial` or `open`, not `derived`.

## Immediate Next Move

Build one small strict bridge registry packet with exactly four initial outputs:

1. mass-ratio layer,
2. `sin2_theta_w_eff`,
3. `alpha_s(mu0, alpha0)` boundary,
4. dimensionless gravity bridge observable.

For each output, record:

1. strict input chain,
2. intermediate objects used,
3. whether any external observable origin is present,
4. whether the result is strict-derived or only bridge-ready,
5. what still blocks promotion to a stronger claim.

This keeps legacy useful as audited background, while moving the actual program onto a narrow, explicit, strict-side bridge to SM/GR observables.
